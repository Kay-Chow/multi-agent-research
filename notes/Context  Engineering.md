## 原则

1. Prompt 只是上下文的一部分，是跟 Agent 说了什么，而 Context 是 Agent 知道什么
2. 完整的 Context = System Prompt + 用户输入 + 对话历史 + 工具定义 + 工具输出 + 记忆模块
3. 上下文窗口是有限制资源，需要精心管理

可以把 LLM 想象成一个超级聪明，但是没有任何背景知识的顾问：

- Prompt Engineering 就是你在会议上对他说的话
- Context Engineering 就是你在会议前，给他准备的全部资料---备忘录、财务报表、相关人员档案等等信息，有了这些信息，这个顾问才能给出最好的建议

## 核心组件

### System Prompt

可以想象它是模型的“宪法”，它定义了模型的身份、行为边界和基本准则。

#### 设计原则

- 角色定义清晰：不能是“你是一个助手”，而是说得明明白白：“你是 XX 公司的客服 Agent，专门···”
- 结构化文本：用 Markdown 标题、列表、分隔符组织内容，LLM 对结构化文本理解更好
- 优先级明确：重要规则放前面（模型对靠前内容的注意力更强）
- 约束与自由的平衡：过度约束会导致僵化，过度自由会导致不可控

### 用户输入

- 用户的当前消息
- 用户画像

### 对话历史

对话历史是最容易失控的上下文组件。

管理策略：

- 滑动窗口：只保留最近的 N 轮
- 摘要压缩：将旧对话压缩为摘要
- 关键帧提取：只保留关键转折点的对话
- 分层存储：近期用滑动窗口保存完整对话，远期保存压缩的摘要，同时还保留关键帧，这是最完整的策略，一般用在生产系统

### 工具定义

工具定义越好，Agent 越容易找到合适的工具，这些定义也会保存在上下文中，所以工具数量不要太多。

### 工具输出

- 函数、API 的返回值
- 数据库、文件查询结果
- Web Search 结果
- 代码输出

### 记忆模块

- 工作记忆：当前 Agent 正在处理的内容，即 Context Window中的内容
- 短期记忆：当前会话的内容
- 长期记忆：过去的经验和知识，一般用向量数据库或者KV存储，或者结构化为文档。长期记忆本身不属于 Context，只有召回的内容才会被放入 Context

## 上下文的管理

### Lost in the Middle

研究证明，LLM 对上下文的头部和尾部的信息关注度最高，中间的信息容易被忽略。

#### 处理方法：

- 把重要信息放头部和尾部
- 使用明确的标题帮助模型定位重要信息，这就是 System Prompt 里说的，结构化文本
- 归根结底，最有效的方法还是减少上下文大小

### Context Rot（上下文腐化）

#### 随着对话轮次的增加，上下文中会积累：

- 过时信息：早起结论可能被推翻
- 矛盾信息：多次修改导致新旧版本共存
- 噪声信息：无关的闲聊，失败的尝试，冗余的确认等
- 指令漂移：模型逐渐偏离原始 System Prompt 的行为规范

#### 应对策略：

- 定期重新注入 System Prompt
- 对话历史主动清洗
- 使用检查点机制，在关键节点创建上下文快照
- 实现上下文健康度监测，监测过时、矛盾和噪声信息

### Token 预算分配

一般大部分预算都会分配给对话历史、记忆模块和工具输出，除此以外，一般都会预留个30%以上的空间，作为安全冗余空间。因为：

- 工具输出大小不可预测，
- 模型在解决窗口上限时性能会下降
- 需要为多轮调用预留空间

### 上下文超 token 预算

那就需要对上下文进行压缩或者裁剪，常见方法有：

- LLMLingua：在把完整 Context 送入 LLM之前，先用一个小模型，比如 GPT2，标注每个 token 的重要性，把不重要的删除，再丢给 LLM
- 摘要压缩，用 LLM 将长文本压缩为摘要
- 选择性加载：只加载与 query 相关的上下文片段
- 分层压缩：越远的内容压缩越狠
- 结构化提取：从非结构化文本提取关键 KV 对

## MCP和SKill

- MCP 是协议层，本身不会放在 Context 里，但 MCP 的工具定义、资源文本、调用结果，则会放 Context 里。所以，MCP 是标准化 AI 模型与外部数据源和工具之间交互的协议，用于生产上下文素材
- Skill 是内容层，SKill 的文本会直接放 Context 里，是给 LLM 读的操作手册
